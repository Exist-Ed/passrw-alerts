## 1. Суть проекта

### ✅ Зафиксировано
- **Источник:** [pass.rw.by](https://pass.rw.by) — сайт Белорусской железной дороги (БЧ) для покупки билетов на поезда.
- **Продукт:** Telegram-бот с Mini App (полноценный UI внутри Telegram, а не просто чат-бот).
- **Проблема:** на нужный поезд все билеты раскуплены, а ехать надо. Места иногда появляются (кто-то сдал билет, добавили вагон), но их быстро раскупают. Сейчас приходится вручную заходить на сайт, искать поезд и проверять, не появились ли места, — и легко не успеть.
- **Решение:** пользователь подписывается на конкретный поезд и типы мест, бот следит за ним и сразу присылает уведомление со ссылкой для быстрой покупки.
- Бот **не покупает** билет: даёт ссылку, пользователь сам авторизуется на сайте и покупает.
- Сервис **бесплатный**, интерфейс **только на русском**.
- **Цели:** портфолио, удобный инструмент для себя, прокачка навыков (Telegram-боты, Mini Apps, NoSQL, основы Docker). Темп — как получится.

## 2. Пользователи

### ✅ Зафиксировано
- Публичный сервис, открыт для всех.
- Нагрузка: на старте 1–5 пользователей, потом около 100 в неделю.
- Лимит: **максимум 3 активные подписки** (3 разных поезда) на одного пользователя — это и есть базовая защита от абьюза.
- На один и тот же поезд (номер + дата) нельзя подписаться дважды: в списке поездов он помечен «Уже ждём места».

---

## 3. Пользовательский сценарий

### ✅ Зафиксировано

**Создание подписки (Mini App):**
1. Пользователь открывает бота → запускается Mini App.
2. Выбирает станцию отправления и станцию прибытия. Оба поля — выпадающие списки с ручным вводом и автокомплитом «как на сайте». Ввод пользователя нормализуется (регистр, «ё/е», лишние пробелы, дефисы).
3. Когда станции выбраны, появляется список поездов, отсортированный по времени отправления. Дата выбирается в календаре (по умолчанию сегодня), есть переключатель «ближайшие 7 дней». Оформление примерно как на сайте: время, номер, маршрут, типы мест, сколько свободно, цена. Поезда без мест помечены «Мест нет», поезда с уже активной подпиской — «Уже ждём места».
4. Пользователь выбирает **один** поезд → выбирает один или несколько типов мест (тарифов, см. 4.2).
   - Если в поезде мест нет совсем, предлагаются все тарифы, характерные для поездов этого класса (`interregional_business`, `interregional_economy`…). Откуда берётся этот список — см. 4.3.
   - **Электрички** (`regional_economy`): подписка есть, но без выбора категорий. Алерт приходит, когда билеты на электричку снова можно купить (см. 4.5).
5. Подписка создана. Mini App закрывается, в чат приходит сообщение «Ждём, пока появятся места на поезд N».

**Если места уже есть в момент подписки** (любое количество): сразу приходит обычный алерт с количеством мест и кнопками.

**Алерт (одно сообщение):**
- Поезд, какие места появились (сгруппированы по тарифам, см. 4.2) и **сколько всего мест свободно** сейчас.
- Ссылка на сайт, по которой залогиненный пользователь максимально быстро доберётся до покупки (см. раздел 6).
- В **этом же сообщении** две кнопки:
  - **«Да, взял билет»** → подписка завершается. Кнопка работает и в старых алертах этой подписки.
  - **«Нет»** → поиск продолжается.
- Если пользователь не нажал ничего, алерты продолжают приходить, пока поезд не отправится.

**«Мои поезда» (раздел в Mini App):**
- Список подписок пользователя с возможностью отменить активную.
- Хранится история подписок со статусами:
  - `ждём место` — активна;
  - `завершено` — пользователь нажал «Да, взял билет»;
  - `отменено` — пользователь отменил сам;
  - `поезд ушёл` — время отправления прошло.

**Если сайт недоступен:** при открытии Mini App показываем плашку «Сайт БЧ сейчас недоступен». Воркер продолжает попытки.

## 4. Логика обнаружения мест и алертов

### ✅ Зафиксировано
- Канал уведомлений — Telegram-чат с ботом, круглосуточно, без «тихих часов».
- Задержка критична: места раскупают быстро.
- Проверка примерно **раз в минуту**: базовый интервал 60 секунд с небольшим случайным разбросом (±10 секунд). Обоснование — в разделе 6, «Частота опроса».
- Защита от «мигания» **не нужна**.

### 4.1. Снапшоты и «новое место»
- Примерно раз в минуту бот делает **снапшот** свободных мест по всем отслеживаемым поездам.
- Опрос общий для всех пользователей: один запрос `/route/` на уникальную тройку (откуда, куда, дата) возвращает сразу все поезда маршрута. Детали по вагонам (`car_places`) запрашиваются только для поездов, где в нужных типах появились места.
- **Новое место** — конкретное место (вагон + номер), подходящее под тарифы подписки, которого не было в предыдущем снапшоте.
- Пример: свободных мест не было → появилось место → алерт → через минуту место забрали → через 10 минут оно снова освободилось → **снова алерт**.
- Если на поезд подписано несколько человек, алерт приходит всем одновременно, каждому по его тарифам.
- **Отдельный скан «всех поездов раз в полчаса» не нужен.** Запрос `/route/` и так примерно раз в минуту возвращает все поезда маршрута за дату. Если добавят вагон или места, это будет видно в ближайшем снапшоте. Новые поезда на маршруте пользователю неинтересны: подписка всегда на конкретный поезд.

### 4.2. Группировка мест — по тарифу
Тариф = тип вагона + класс обслуживания + флаги (велосипед, для людей с инвалидностью). В ответе `car_places` каждый вагон относится ровно к одному тарифу, поэтому пересечений нет. Тарифы — это и категории для выбора в Mini App (с понятными названиями вместо кодов).

```
🚆 758Б Минск → Гомель, 17 окт, 17:25
Появились места:
• Сидячий (2П) — 2 места
• Сидячий с велосипедом (2Р) — 1 место
Всего свободно в выбранных категориях: 3
[ссылка]
[Да, взял билет] [Нет]
```

### 4.3. Каталог тарифов по классам поездов
Нужен для поездов, где мест нет (сайт не показывает их состав). Каталог «класс поезда → тарифы» **накапливается сам** из ответов сайта, которые мы и так получаем: поиски в Mini App и снапшоты. Отдельный процесс, который регулярно сканирует сайт ради каталога, не делаем: это лишняя нагрузка, и такой опрос как раз попадает под запрет из пункта 81 (раздел 6). На старте каталог заполняем результатами ресерча (раздел 6, «Типы вагонов и классы поездов»).

Важно: внутри одного класса составы различаются, особенно у `international`. Поэтому каталог — это **надмножество** («что бывает в поездах этого класса»), а не точный состав конкретного поезда. Пользователь может выбрать тариф, которого в его поезде нет; тогда алерт просто не придёт. В Mini App стоит подписать: «Состав поезда неизвестен, показаны все возможные типы мест».

### 4.4. Места исчезли
Если все места раскупили, пока пользователь думал, **ничего не делаем**: старый алерт не редактируем и новых сообщений не шлём. Подписка остаётся активной.

### 4.5. Электрички
- Подписка без выбора категорий.
- Сигнал — **статус продажи** поезда на странице `/route/`: флаг `ticket_selling_allowed` и плашка «Мест нет». Количества мест и номеров у электричек на сайте нет.
- Алерт приходит при переходе «продажа закрыта / мест нет» → «можно купить». Если в момент подписки билеты уже продаются — сразу алерт «Билеты есть», как и у обычных поездов.
- ⚠️ В скане ни одной электрички без мест не встретилось: билеты на места без номеров, похоже, почти никогда не заканчиваются. Как выглядит «мест нет» у электрички, пока не видели. Если такой случай встретится, парсер должен его распознать (заложить логирование необычных состояний).

## 6. Ресерч pass.rw.by (результаты, 2026-10-15)

### Итог
Сложную вёрстку парсить почти не придётся. У сайта есть внутренние эндпоинты, которые работают без авторизации и без капчи, а два из них отдают JSON. Антибота при обычных запросах не видно, сайт доступен из-за пределов Беларуси. **Главный риск — правила сайта (см. ниже).**

### ⚠️ Правила сайта
Отдельного пользовательского соглашения на сайте нет. Ближе всего [Правила оформления и использования электронных билетов на поезда с нумерованными местами](https://pass.rw.by/ru/help/travel-documents-tickets/electronic-travel-documents/rules-of-registration-and-use-of-electronic-travel-documents-tickets-on-trains-with-numbered-seats-.html), раздел 11 «О нарушениях порядка пользования сервисами БЧ».

> **81.** Учетная запись пользователя подлежит блокировке в следующих случаях нарушения порядка использования сервисов сайта и приложения: оформление электронных билетов с использованием роботизированных запросов (операций)…; многократное резервирование без последующей оплаты…; **регулярные поисковые запросы по отдельным направлениям, при этом запросы направляются по определенному временному шаблону (каждый час в определенное время / каждые N минут и т.д.).**

Что это значит для нас:
- Регулярный опрос маршрута по расписанию — ровно то, что делает наш воркер, и правила прямо называют это нарушением.
- Санкция в правилах — **блокировка учётной записи**. Мы опрашиваем без авторизации, так что блокировать нечего, а аккаунты пользователей не затрагиваются: они только переходят по ссылке и покупают как обычно. Реальный риск — **блокировка IP** сервера или появление капчи / антибота.
- Раз БЧ явно формулирует такое правило, значит, они такие запросы отслеживают. Долгий тест опроса (см. «Что ещё проверить») становится важнее.
- Минимизируем нагрузку: опрос примерно раз в минуту, один запрос на маршрут-дату для всех пользователей, `car_places` только при появлении мест, кэш поисков в Mini App, станции из своей базы.
- ✅ **Решение:** это пет-проект, риск блокировки IP принят осознанно. ⚠️ Пока воркер живёт на домашнем сервере, бан ляжет на домашний IP — сайт БЧ может перестать открываться у всех в домашней сети (и при покупке билетов тоже). План Б: перенести воркер на дешёвый VPS. Если сервис станет популярным, честный путь — написать в БЧ про доступ к данным.

### robots.txt — что это значит
`robots.txt` запрещает `/*/ajax/*` (автокомплит и `car_places`). Это **не техническая блокировка и не закон**, а инструкция для поисковых роботов (Google, Яндекс): «не индексируй это». Эндпоинты работают, мы ими пользоваться **можем**. Но это ещё один сигнал, что владелец не рассчитывает на автоматические обращения к ним. Поэтому:
- **Автокомплит станций** делаем по своей базе: один раз выгружаем справочник станций (он почти не меняется) и ищем по нему локально. Mini App при каждом нажатии клавиши в сайт не ходит.
- **`car_places`** вызываем только тогда, когда `/route/` показал места в нужных тарифах.

### Эндпоинты

| Что | Запрос | Формат | Для чего нам |
|---|---|---|---|
| Автокомплит станций | `GET /ru/ajax/autocomplete/search/?term=Минск` | JSON: название, `exp` (код станции), координаты | Разовое наполнение справочника станций |
| Поезда на маршруте за дату | `GET /ru/route/?from=Минск&from_exp=2100000&to=Гомель&to_exp=2100100&date=2026-10-17` | HTML (~350 КБ, ~1.5–2 с) | Список поездов + число свободных мест по типам; основа снапшота |
| Места в вагонах | `GET /ru/ajax/route/car_places/?from=2100000&to=2100100&date=2026-10-17&train_number=612Щ&car_type=4` | JSON: тарифы → вагоны → **номера свободных мест**, верх/низ, цены | Детали для алерта и сравнения снапшотов |

### Что есть в данных
- **По каждому поезду** (страница `/route/`): номер, `train-id` (например `1_612Щ_1792257960_1792270740`), тип поезда (`interregional_economy`, `interregional_business`, `international`…), время, длительность, флаг `ticket_selling_allowed`, и по каждому типу вагона — название, код `car_type`, число свободных мест и цена.
- **Типы мест и классы поездов** — см. отдельный подраздел ниже. Флаги тарифа:
  - `is_bike_allowed` — места с велосипедом;
  - `is_special` — места для людей с инвалидностью.
- **Поезд без мест:** вместо списка типов пишется «Мест нет», и **состав поезда не виден.** Пример: поезд 758Б Минск → Гомель 17.10.
- **По вагону** (`car_places`): номер вагона, перевозчик, список свободных мест (`"017", "018"…`), количество верхних/нижних.

### Ответы `car_places`, когда мест нет
| Ситуация | Ответ |
|---|---|
| Поезд полностью без мест (758Б), любой `car_type` 1–6 | `200`, тело `{"e":{"exceptions":[{}],"friendly":[{}]}}` — ошибка без текста |
| В поезде есть места, но запрошенного типа вагона нет (612Щ, `car_type=2`) | `200`, обычный JSON с `"tariffs": []` |

Оба случая трактуем как «0 свободных мест». Отличить «типа нет в составе» от «всё раскуплено» по этому эндпоинту нельзя, поэтому выяснить состав поезда без мест через него не получится (это подтверждает решение с каталогом из 4.3). Ответ с ключом `e` — штатная ситуация, а не сбой парсера.

### Типы вагонов и классы поездов
Скан 17 маршрутов на 22.10.2026 (111 поездов: Минск → Брест, Москва, Санкт-Петербург, Гродно, Витебск, Могилёв, Полоцк, Пинск, Калининград, Молодечно, Орша, Барановичи, Лида, Жлобин; Гомель → Брест, Санкт-Петербург; Брест → Москва).

**Типы вагонов (`car_type`):**

| Код | Название | В каких классах поездов |
|---|---|---|
| `0` | (без названия) — места без номеров | `regional_economy` |
| `2` | Сидячий | `international`, `interregional_business`, `interregional_economy`, `regional_business` |
| `3` | Плацкартный | `international`, `interregional_economy` |
| `4` | Купейный | `international`, `interregional_economy` |
| `6` | СВ | `international` |

Коды `1` (общий) и `5` (мягкий) ни разу не встретились; по нумерации они, вероятно, существуют, но в текущем расписании таких вагонов нет. Парсер должен спокойно принимать неизвестные коды.

**Классы поездов → тарифы (тип вагона / класс обслуживания / флаги):**

| Класс поезда | Тарифы |
|---|---|
| `interregional_business` (межрегиональные бизнес) | Сидячий `1С`, `2П`, `2П` + для инвалидов, `2Р` + велосипед |
| `regional_business` (региональные бизнес) | Сидячий `1С`, `2П`, `2П` + для инвалидов, `2Р` + велосипед |
| `interregional_economy` (межрегиональные эконом) | Сидячий `3С`; Плацкарт `3Б`, `3Д`, `3У`; Купе `2К`, `2У` |
| `international` (международные) | Сидячий `1Р`, `2Ж`, `2Ж` + для инвалидов, `2Р`, `2Ю`; Плацкарт `3Б`, `3Д`, `3У`, `3Э`; Купе `2Б`, `2К`, `2У`, `2Ф`, `2Ш`; СВ `1Б`, `1У` |
| `regional_economy` (электрички) | без нумерованных мест и без категорий — подписка «на поезд целиком», см. 4.5 |

Наблюдения:
- Код класса обслуживания сам по себе не уникален: `2Р` в бизнес-поездах — с велосипедом, а в международных — без. Тариф = код + флаги + тип вагона.
- **Электрички (`regional_economy`)**: количество мест не показывается, места без номеров, кнопка «Купить билет» вместо «Выбрать места», `car_places` с `car_type=0` возвращает ошибку `{"e":…}`. Из всех 16 электричек Минск → Молодечно у всех `ticket_selling_allowed=true` и нет плашки «Мест нет». Единственный доступный сигнал — этот флаг и плашка.

### Ссылка для покупки
- Кнопка «Выбрать места» на сайте — это POST-форма на `/ru/order/places/` с сериализованными данными маршрута. GET на этот адрес редиректит на главную, поэтому **прямой ссылки на выбор мест нет**.
- Покупка без авторизации запрещена (`isUnauthorizedPurchaseAllowed = false`).
- **Якорь не работает** (проверено в Chrome): у строк поездов в DOM нет `id` (`train-id` лежит только в атрибуте `data-train-id`), а скрипт сайта при загрузке ещё и удаляет `#…` из адреса. Страница просто прокручивается к началу списка.
- Страница поезда `/ru/train/?train=…` — только расписание по станциям, кнопки покупки там нет.
- **Итоговый вариант:** ссылка на страницу маршрута за дату. На маршруте обычно 5–25 поездов, поэтому в алерте **крупно пишем номер поезда и время отправления**, чтобы пользователь быстро нашёл его в списке и нажал «Выбрать места».

### Нагрузка и доступность
- 8 запросов подряд без пауз: все `200`, без капчи и блокировок. Перед сайтом стоит защита `HosterGuard` (ставит cookie), но обычному curl она не помешала.
- Сайт открылся с немецкого IP → можно хостить вне Беларуси.
- Отдельного API для разработчиков нет: раздел `/ru/dev/` — «Раздел недоступен».

### 🚫 Результат теста опроса (2026-10-15, с Mac, IP в Германии)
- Опрос 2 маршрутов раз в ~60 секунд (≈2 запроса в минуту).
- **Первые ~10 минут** (18 запросов) — нормальные ответы.
- **С 23:10 и до конца теста (1 час)** — на любой запрос, включая главную страницу, приходит `200` и заглушка «Verification» (1261 байт) вместо данных. Через час после остановки теста заглушка всё ещё отдаётся.
- Это JS-проверка HosterGuard: страница выполняет вычисление, проверяет `navigator.webdriver` (признак автоматизированного браузера), ставит cookie `hg-security` на 2 минуты и перезагружается. Обычный браузер проходит её автоматически и незаметно, поэтому **люди с этого IP сайтом пользоваться могут**. Блокируются именно скрипты.
- **Блокировка временная:** последний заблокированный ответ — около 00:01, первая проверка в 00:22 уже вернула нормальные данные. То есть блок снимается **не позже чем через ~20 минут** после прекращения запросов. Пока запросы шли, блок не снимался (похоже на скользящее окно).
- Вывод: защита от ботов на сайте активная и срабатывает быстро. Опрашивать сайт раз в минуту простым HTTP-клиентом **не получится**.
- Обходить проверку (вычислять cookie за браузер, подделывать признаки браузера) не делаем: это прямой обход защиты сайта от автоматизации вдобавок к запрету из пункта 81.

### Частота опроса (до теста)
Решение: примерно **раз в минуту**. Вопрос был: есть ли смысл делать интервал случайным в диапазоне 30 секунд – 2 минуты?

- **Против широкого разброса:** средняя задержка при 30–120 секундах ≈ 75 секунд, а в худшем случае 2 минуты. Это хуже фиксированной минуты, а места разбирают быстро.
- **Незаметнее это не делает:** запросы всё равно идут с одного IP, с одинаковыми заголовками, по одному маршруту, ~1000–1400 раз в сутки. Такое легко отследить по объёму и без строгого расписания. По сути это всё тот же «регулярный поисковый запрос» из пункта 81, а риск бана ты уже принял.
- **За небольшой разброс (±10 секунд):** он нужен для инженерной гигиены. Если отслеживаются несколько маршрутов, их запросы не уходят одной пачкой в одну секунду, а распределяются по минуте. Плюс при ошибках сайта — экспоненциальная пауза (backoff), а не долбёжка каждые 60 секунд.

Итого: **60 секунд ± 10 секунд**, маршруты разнесены по времени, backoff при ошибках. Интервал выносим в конфиг, чтобы его легко было менять.

## 8. Технологии и инфраструктура

### ✅ Зафиксировано
- Telegram Bot API + Telegram Mini App.
- Бэкенд на **Python**.
- Хостинг: пока **домашний сервер**, позже — возможно, VPS. Сайт БЧ доступен из-за рубежа.
- Всё запускается локально в **Docker**.

### ✅ Стек

| Часть | Предложение | Почему |
|---|---|---|
| Бот | **aiogram 3** | Самый популярный асинхронный фреймворк для Telegram-ботов на Python |
| API для Mini App | **FastAPI** | Асинхронный, современный, автодокументация; проверка `initData` от Telegram |
| Воркер (снапшоты) | asyncio-цикл + **httpx** + **selectolax** / BeautifulSoup | Асинхронные HTTP-запросы и быстрый парсинг HTML |
| Фронтенд Mini App | **React + Vite + TypeScript** + [`@telegram-apps/telegram-ui`](https://github.com/Telegram-Mini-Apps/TelegramUI) | Самый популярный вариант для Mini Apps: готовые компоненты в стиле Telegram (тёмная/светлая тема), много примеров. JS знать не обязательно — основную часть кода напишу я, а ты будешь читать и править |
| База | **MongoDB** (документная NoSQL) — единственная база | Самая популярная NoSQL-база, часто встречается в дата-инженерии; подписки, снапшоты и алерты естественно ложатся в документы. Кэш поисков Mini App — коллекция с TTL-индексом (документы удаляются сами) |
| Дашборд | **Metabase** | См. раздел 7 |
| Запуск | **docker compose** | Бот, API, воркер, MongoDB, Metabase — одной командой |

**Подходит ли NoSQL под задачу?** Да. Данных мало, связей между сущностями почти нет: пользователь → подписки → алерты. Снапшот (набор мест по вагонам) — это естественный JSON-документ. SQLite или Postgres тоже справились бы, так что NoSQL здесь — осознанный выбор ради навыка, а не необходимость. Это нормально.

**Почему без Redis.** Redis — тоже NoSQL, но другого типа: хранилище «ключ → значение» в оперативной памяти, обычно как кэш или очередь рядом с основной базой. При нашей нагрузке MongoDB закрывает всё сама (последний снапшот — документ, кэш — TTL-коллекция), так что второй сервис только усложнит проект. Если позже захочется изучить Redis — его легко добавить для кэша.

**Нюанс с лицензиями:** MongoDB Community бесплатна и спокойно работает в Docker, но её лицензия SSPL формально не считается open source. Для пет-проекта это неважно; строго open source-замена — FerretDB.

**Docker как цель обучения.** Docker не прячем за готовыми шаблонами, а собираем по шагам, чтобы разобраться в основах:
1. Один `Dockerfile` для Python-сервиса (бот): образ, слои, `COPY`, `RUN`, `CMD`, `.dockerignore`, кэш сборки.
2. Готовые образы из Docker Hub: MongoDB и Metabase через `docker run` — порты, переменные окружения, volumes (чтобы данные не пропадали).
3. `docker compose`: несколько сервисов, общая сеть и обращение друг к другу по имени сервиса, `depends_on`, healthcheck, `.env`-файл для секретов (токен бота).
4. Мультистейдж-сборка для фронтенда (Node собирает → nginx раздаёт статику).
5. Логи, `exec` внутрь контейнера, рестарт-политики — то, что нужно для жизни на домашнем сервере.

Каждый шаг — с коротким объяснением в README проекта.

**Домашний сервер и Mini App:** Telegram открывает Mini App только по публичному **HTTPS**-адресу. Для домашнего сервера (и для локальной разработки) понадобится туннель — **Cloudflare Tunnel** (бесплатно, стабильный адрес) или ngrok. Бот при этом может работать в режиме long polling, и публичный адрес ему не нужен.

### Прокси — что это
Прокси — промежуточный сервер: запрос к сайту уходит не с твоего IP, а с IP прокси. Обычно прокси используют, когда сайт блокирует IP за частые запросы, чтобы распределить запросы по многим адресам.

**Рекомендация: не закладываем.** При нашей нагрузке (несколько маршрутов, один запрос на маршрут примерно раз в минуту) они не нужны. А использовать прокси, чтобы обойти бан, значит сознательно обходить защиту сайта при уже явном запрете в правилах (пункт 81). Если после долгого теста окажется, что сайт банит, правильнее снизить частоту опроса или договариваться с БЧ.
